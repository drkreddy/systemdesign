Turning a CDN on caches nothing

The most disorienting result in this whole lab: send a perfect caching header, put a CDN in front, and watch every single request still travel to Oregon.

Here is a response the lab's API sends. There is nothing wrong with it:

Cache-Control: public, max-age=300

Public, cacheable, good for five minutes. Four requests through Cloudflare produced four DYNAMIC responses and four trips to Oregon. Not one was cached.

Two decisions that look like one

Cloudflare decides whether something may be cached from its file extension — roughly .js .css .jpg .png .svg .woff .pdf. An address like /api/time has no extension, so it is ineligible, and an ineligible response never has its Cache-Control examined at all.

That is why a JavaScript file cached with zero configuration while a JSON API refused to, no matter what it sent. To cache the API you must first tell Cloudflare it is allowed to, with a Cache Rule.

Not universal

This is a Cloudflare choice, not how the web works. Fastly and Akamai honour Cache-Control for any content type. Cloudflare's default is the conservative one — it won't accidentally cache a logged-in user's dashboard. Worth knowing which kind of CDN you're holding.

Run it: an endpoint that will never cache

This one sends no-store. The Cache Rule allows caching; the header declines. Every request goes to Oregon, and the timestamp in the response changes every time.

One word tells you which gate failed

Every Cloudflare response carries cf-cache-status. Two of its values are a precise diagnosis, and knowing the difference saves hours:

ValueMeansFix
HITserved from the edge; your server never heard about itnothing — this is the goal
MISSallowed, but no copy was held; fetched and storednothing; the next one should HIT
DYNAMICgate 1 failed. Never consideredyour Cache Rule
BYPASSgate 2 failed. Allowed, but a header said noyour Cache-Control
EXPIREDwas cached, time ran out, had to revalidatelonger TTL, or serve stale (post 5)

When the lab's Cache Rule was added, /api/time moved from DYNAMIC to BYPASS. Nothing about the endpoint changed — the rule granted permission and the header declined it. That is the design you want: the rule grants permission, the header exercises it, so the application keeps control per endpoint instead of the CDN making blanket decisions.

Browsers and CDNs can be told different things

max-age vs s-maxage
max-age talks to everyone, browsers included. s-maxage talks only to shared caches like a CDN.
Cache-Control: public, max-age=0, s-maxage=300

This says: browsers, always check with me; CDN, shield my server for five minutes. Measured, it produced a MISS then three HITs at the edge despite max-age=0. It is the workhorse pattern for dynamic content — users get fresh data while your database sees one request per five minutes per city instead of one per visitor.
