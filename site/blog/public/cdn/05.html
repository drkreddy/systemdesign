Fresh, stale, and serving old data on purpose

When a cached copy expires, the obvious move is to make the next visitor wait for a fresh one. There is a much better option.

A cached object has a lifetime. When it runs out, something has to happen, and the naive answer punishes whoever happens to arrive at that moment — they pay the full journey to Oregon so that everyone after them doesn't.

Stale-while-revalidate takes a different view: hand that visitor the slightly-old copy immediately, and fetch the new one in the background. Nobody waits.

Run it: watch one object age

This experiment has a 5-second freshness window and a 10-second stale window, so the whole lifecycle fits inside one page view. Watch for the STALE row — it is served just as fast as a hit, from a copy the edge knows is out of date.

Measured against an origin deliberately taking 2000ms to respond, a request arriving in the stale window returned in 165ms. The refresh happened afterwards, invisibly.

Cloudflare's free plan doesn't do this

Sending stale-while-revalidate in a header and testing it produced EXPIRED — meaning the visitor waited for the full round trip. Serving stale is a paid feature.

So the edge worker behind these posts implements it by hand. The interesting part isn't the idea, it's a subtlety that made the first version silently useless.

The bug that reported perfect health

A cache API will refuse to return an entry that has expired according to its own headers. Storing a copy with a lifetime equal to the fresh window therefore deletes it at exactly the moment the stale window opens — leaving nothing to serve stale. The feature never fires, and the symptom is an ordinary-looking MISS, which reads as a cold cache rather than a bug.

The fix: store with a lifetime covering fresh + stale, and track freshness yourself with a timestamp. The cache's idea of "expired" and your application's idea of "stale" have to be different things — otherwise serve-stale cannot be built at all. That holds for Redis and Memcached just as much as for a CDN.

The worse bug underneath it

The second version looked like it worked. Cache statuses cycled MISS → HIT → STALE → HIT, ages reset correctly, responses were fast.

The content was frozen permanently.

A cache that is stale forever is worse than no cache, because it is silent. The only thing that caught it was the counter on the origin server, which had been sitting there the whole time reading 1.

The rule this generalises to

When you put a cache in front of something that is already cached, revalidation silently reads the inner cache. Identical trap with an application cache over a database replica, or Redis over a query cache. Always check freshness against the real source of truth, never against the layer immediately beneath you.
