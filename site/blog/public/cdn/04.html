How cache keys shatter

A site with flawless caching headers can still run a terrible hit rate, because of characters other people append to your URLs.

A cache files each copy under a key. By default that key is the full address, including everything after the ?. Two requests share a cached copy only if their keys match exactly.

Now consider five people sharing the same page from different places:

/article                                HIT
/article?utm_source=twitter             MISS
/article?utm_source=facebook            MISS
/article?fbclid=abc123                  MISS
/article?utm_source=x&utm_medium=social  MISS

Four journeys to Oregon for what any human would call one page. You didn't add those parameters — Facebook, Google Ads and email tools did, on the way in.

cache key
The label a cached copy is stored under. Change one character and, as far as the cache is concerned, it's a different object entirely.

Run it: fragment a cache, or don't

The lab's edge strips tracking parameters before computing the key. So the decorated URLs below should all land on the same cached copy — one MISS, then hits.

Getting that behaviour took writing code. On Cloudflare's free plan, choosing which parameters count toward the key is an Enterprise feature — the dashboard shows the option greyed out. The edge worker here does it in about ten lines:

const kept = [...url.searchParams.entries()]
  .filter(([k]) => !TRACKING.some(re => re.test(k)))
  .sort(([a], [b]) => a.localeCompare(b));

The sort matters too: ?a=1&b=2 and ?b=2&a=1 are the same resource, and without sorting they are two cache entries.

The one that isn't a performance bug

HTTP has a header for "my answer depends on this request header". Vary: Accept-Language should give each language its own cached copy. Here is what actually happened when the lab tried it:

Visitor asked forCache statusWhat they received
en-USMISSEnglish — correct
fr-FRHITEnglish — wrong
ja-JPHITEnglish — wrong
de-DEHITEnglish — wrong

Cloudflare honours Vary: Accept-Encoding and ignores every other value. It cached one copy and served it to everybody.

Notice the shape of that failure. A correct shared cache would fragment per language and your hit rate would collapse — annoying, visible, easy to spot. This does the opposite: the hit rate stays beautiful and the answers are wrong.

Why this is a security bug

Picture an application that ships Cache-Control: public, max-age=60 alongside Vary: Cookie, reasoning that each session gets its own entry. Behind a CDN that ignores Vary, the first user's personalised response is cached and served to every subsequent visitor. That isn't a slow page. That's one customer seeing another customer's account.

Every wrong answer above was a healthy-looking HIT. No cache-status check could have caught it. Only comparing the body against what was requested exposed the problem.

What to do instead

  • Put the variation in the address — /fr/page, ?lang=fr. Then it's part of the key and cannot be confused.
  • Put it in the key explicitly, via edge code or cache-key configuration.
  • Mark genuinely per-user content private, no-store and keep it away from shared caches altogether.

The general lesson outlives Cloudflare: Vary is the least reliably implemented corner of HTTP caching. Never rely on it for correctness at a CDN.

The habit

When you test a cache, assert on what came back, not on what the cache says it did. Both failures in this post were invisible to the metrics people normally watch.
