The thundering herd

Every cache empties at the same moment, and every one of them asks your server the same question at the same moment.

The setup has appeared three times already without being the subject. Caches are per-city, so ten cities means ten independent fetches. Expiry isn't staggered, so popular objects go cold together. And clearing a cache empties every city simultaneously.

That last one is measurable. One purge of one file, measured across ten cities:

MomentResultGlobal median
Before the purgemostly HIT132ms
Immediately afternot yet propagated164ms
60 seconds after7 MISS, 1 HIT549ms

One purge made the site four times slower worldwide, because every city lost its copy and went back to Oregon at once.

Run it: fire ten requests simultaneously

This asks for a slow, uncached object from ten parallel requests at once. Watch how many actually reach the origin.

What I got wrong here

My prediction was that 60 concurrent misses would produce 60 origin requests. The measured answer was 2.

Cloudflare recognises identical in-flight requests to the same origin object and collapses them into one. That protection is free, automatic, and contradicts the usual telling of this story. If you have been told that N simultaneous misses means N database queries, measure it before believing it.

request coalescing
When several identical requests arrive while one is already in flight, the cache waits for that one and answers them all from its result. Applies per city — which is precisely its limit.

The distinction that actually matters

The same burst of 40 requests, differing only in when it arrived relative to the cached copy's lifetime:

Load arrivesCache statusTotal waitReached the origin
inside the stale window40 × STALE0s2
past the stale window39 × MISS3s2

Identical cost to the origin. Completely different experience for the visitor. That gap is the real lesson:

  • Coalescing protects the origin. It stops 40 requests becoming 40 database queries.
  • Serving stale protects the user. It stops those 40 people waiting while the one query that does run completes.

They solve different halves of the problem, and you need both. The second one you have to build yourself, as post 5 describes.

The defences, honestly rated

DefenceAvailable freeProtects
per-city request coalescingyes, automaticthe origin
stale-while-revalidatebuild it yourselfthe user
jittered lifetimesbuild it yourselfthe origin, against synchronised expiry
versioned filenamesyesavoids invalidation entirely
tiered cache / origin shieldpaid onlythe origin, across cities

Jitter is the cheapest thing on that list and the most overlooked. If everything cached during a traffic spike is given exactly the same lifetime, it all expires together and recreates that spike against your origin, on a loop. Scattering each lifetime by ±15% breaks the synchronisation permanently.

The cross-city gap is real and cannot be closed on a free plan. A purge still costs one origin fetch per city. The free mitigations are long stale windows, and preferring a version bump over a purge whenever you can.

The best strategy is not needing any of this

Files named after their contents — app.a3f9b2c.js — never need invalidating. New content means a new address, so the old copy simply stops being requested and ages out unused. No purge, no propagation delay, no stampede.

It only works for content referenced indirectly, through HTML that itself has a short lifetime. You can't version /api/products, because visitors ask for that address by name. But for everything you can, it beats every other option on this page.

The thread running through all six posts

Every serious bug here was invisible in the metrics people normally watch. Wrong-language content served as a healthy HIT. A permanently frozen cache reporting perfect statuses. A stale-serving feature that silently never fired. Each was caught by one thing: a counter on the origin that answered "did this actually reach me?" — a question no cache header can answer honestly about itself.
