Why distance is the whole problem

Your server is in one place. Physics charges you for every visitor who isn't near it, and no amount of optimisation buys that back.

The lab behind these posts is a small Node server in Oregon. From India, a request to it travels roughly 13,000 km, and the answer travels 13,000 km back. Light in fibre covers about 200,000 km per second, and real network paths are nothing like straight lines, so that round trip costs somewhere around 200 milliseconds.

That number is not a performance problem you can fix. Your code could run in zero time and the visitor still waits. The only way to make it go away is to stop making the journey.

origin
Your real server, the only thing that can generate new content. Here, the Node app in Oregon.
edge, PoP, colo
Three words for the same thing: a CDN data centre near your visitor. Cloudflare has 300+. They show up in response headers as three-letter codes — BOM Mumbai, SIN Singapore, NRT Tokyo.

Run it: the same request, four times

This asks the lab for a deliberately expensive response. The first request has to reach Oregon. The rest should not.

The shape is the point. One slow request, then a cliff. Nothing about the server got faster; the second request simply never went there.

What TTFB means, and why it's the number that moves

A request isn't one action, it's five, and only one of them changes when caching starts working.

TTFB — time to first byte
The gap between finishing your request and the first byte of the answer arriving. It bundles three things: your request travelling out, the server thinking, and the first byte travelling back.

That "server thinking" part is genuinely inside it. Asking the lab's origin to sleep for a fixed time moves TTFB by exactly that much:

Origin told to sleepMeasured TTFBReading
0 ms0.69 spure travel time
1000 ms1.38 stravel + 1s of work
3000 ms3.31 stravel + 3s of work

TTFB = round trip + server work, and a cache hit deletes both at once. That is why it is the only segment worth watching when you are judging whether a CDN is helping.

Worth knowing early

Speed alone can't prove a cache hit — a fast response might just be a warm connection. The lab's origin counts every request that reaches it, so a counter that stops moving is proof the edge answered. Throughout these posts, that counter is the evidence; the cache status header is only a claim.
