Rate limiting · post 1 of 5

Counting requests is harder than it looks

Every rate limiter answers one question — has this client had too many? — and the obvious way to answer it is wrong in a way you can exploit deliberately.

A rate limiter exists because capacity is finite and demand is not. It shows up in four different jobs that look similar and aren't:

PurposeWhat you're really protecting
Capacitythe service staying up when one client misbehaves
Fairnessone noisy tenant not starving the quiet ones
Costyour bill, when each request costs real money downstream
Abusecredential stuffing, scraping, enumeration

Those want different things. A fairness limiter should be generous to bursts and strict on sustained load. An abuse limiter should be the opposite. Picking an algorithm without deciding which job you're doing is how people end up with limits that block real users and miss real attackers.

The obvious implementation

Divide time into windows. Count requests per window. Refuse anything over the limit. Reset the counter when the window ends.

window = floor(now / 60s)
if window != current: current = window; count = 0
if count < limit: count++; allow
else: refuse with 429

It's a handful of lines, needs one counter per client, and is the first thing almost everyone writes. Against ordinary traffic it behaves exactly as advertised:

allowed refused dashed lines mark window boundaries

Steady traffic at exactly the limit passes untouched. A ramp-up gets throttled once the budget is spent. A mid-window burst of double the limit gets exactly half through. All correct, all what you'd want.

limit and window
The two numbers that define the policy: "100 requests per minute" is a limit of 100 and a window of 60 seconds. Almost every limiter is a different answer to how you measure the window.
429 Too Many Requests
The status code for "you're being limited". Distinct from 503, which means the server is struggling, and from 403, which means you're not allowed at all. Post 5 covers what else belongs in that response — the answer is more than just the status code.

The hole

Look at the dashed lines in the widget above. The counter resets on a boundary that is a property of the clock, not of the client — and it's a boundary the client can calculate exactly as easily as the server can.

If the window resets at the top of every minute, and you know that, then the limit is not really per minute. It's per minute measured from a moment you get to choose.

Try predicting it

A limit of 10 per minute. A client sends 10 requests at 0:59, then 10 more at 1:01. Twenty requests in two seconds. How many does a fixed window allow?

The answer is in post 2, and it's worse than most people guess.

The rest of this lab is about closing that hole, and about what you give up to close it — because every fix costs either memory, accuracy, or both.
