Saying no properly

Four posts on deciding whether to refuse. This one is about the refusal itself — which is where most implementations quietly become part of the problem.

A client that gets refused has to decide what to do next, and it decides using only what you told it. Send a bare 429 with an empty body and you have told it nothing. It doesn't know whether to retry in a second or an hour, whether the limit is per-second or per-day, or how much budget it has left.

So it guesses. Usually it retries immediately, because that's the default in most HTTP clients. A vague refusal converts one blocked client into a client hammering you continuously — you've spent the effort to reject the request and gained nothing, because it comes straight back.

Trip it yourself

This is a real token bucket running at the edge, holding state for you specifically. The first requests pass, the rest are genuinely refused. Nothing breaks and nothing is left in a bad state — waiting a second or two restores your budget.

Watch the 429 rows: each carries how many requests you have left and how long to wait. That second number is the difference between a client that behaves and a client that doesn't.

What belongs in a refusal

HeaderSaysWhy it matters
Retry-Afterwait this many secondsthe one that stops retry storms
X-RateLimit-Limityour total budgetlets a client pace itself before being refused
X-RateLimit-Remainingwhat's leftturns limiting into something clients can plan around
X-RateLimit-Resetwhen it refillsuseful for batch clients scheduling work

Send the last three on successful responses too, not just refusals. A client that can see its budget shrinking can slow down before it hits the wall; one that only learns at the moment of rejection cannot.

Retry-After has to be true

If you say one second and the budget actually returns in five, a well-behaved client retries at one second, gets refused again, and now retries four times instead of once. A dishonest Retry-After creates the exact traffic it was meant to prevent, and it does so specifically among the clients that were trying to cooperate.

The limiter above computes it from the actual token deficit — how long until one whole token exists — rather than a fixed guess. Verified: refused immediately, and allowed after exactly the wait it asked for.

Which status code

CodeMeansUse when
429too many requeststhey exceeded their limit — almost always this
503service unavailableyou are shedding load, not enforcing a quota
403forbiddennever for limiting — implies a permissions problem

The 429/503 distinction is worth keeping straight because clients treat them differently. A 429 says you did too much; a 503 says we are struggling. Monitoring that conflates them will show a limiter working correctly as though it were an outage.

The client's half

Even a perfect refusal fails if clients retry badly. Two things matter, and the second is the one people skip.

Back off exponentially. Wait 1s, then 2s, 4s, 8s. A client retrying at a fixed interval never lets you recover.

Add jitter. If a thousand clients are refused at the same moment and all back off by exactly one second, they return as a synchronised wave — and you refuse them all again, one second later, forever. Randomising each delay spreads them out.

delay = base * 2**attempt
sleep(random(0, delay))     // full jitter
You have seen this before too

In the CDN lab, cached objects were given lifetimes jittered by ±15% so that everything cached during a spike didn't expire together and recreate that spike on a loop.

Same problem, opposite end of the wire. Synchronised clients are the failure mode; randomness is the fix. Any time many actors react to the same event at the same instant, you need to spread them deliberately.

The through-line, and it's the same one the CDN lab kept landing on: the interesting failures are invisible in the obvious metrics. A fixed window under attack reports that it never exceeded its limit, and it's telling the truth about its own counters. A per-instance limiter reports correct enforcement on all eight servers while the client sails past by eight times. In both cases you have to measure the thing you actually care about, from outside, rather than trusting a component's report about itself.
