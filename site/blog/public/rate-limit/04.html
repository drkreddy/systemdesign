Rate limiting · post 4 of 5

Your limit is multiplied by your server count

Everything so far assumed one limiter holding one set of counters. That assumption survives exactly as long as you run one server.

Put the same code on eight servers behind a load balancer and each one counts in its own memory. Each faithfully enforces "10 per minute". The client, whose requests are spread across all eight, gets eighty.

Nothing is broken. Every instance is doing exactly what you told it. The limit you configured simply isn't the limit anyone experiences.

allowed refused

Drag the server count and watch the total. The effective limit is servers × configured limit, and it changes every time you scale — which means your rate limit silently loosens under exactly the traffic that made you add capacity.

You have already seen this shape

In the CDN lab, warming the cache in Singapore did nothing for Tokyo, because each location caches independently — one object cost nine origin fetches across ten cities.

This is the same fact wearing different clothes. State that lives per-instance behaves per-instance, whether it's a cached page or a request counter. Anything you want to be globally true has to be stored somewhere global, and that costs a network hop.

Fix 1: divide the limit by the server count

The arithmetic is obvious — eight servers, so give each a limit of 1.25. It fails for three separate reasons, any one of which is enough.

Traffic isn't evenly spread. Round robin approximates it; least-connections doesn't; a client with keep-alive connections may land on one server for minutes. Switch the widget's routing to random and watch the per-server counts diverge. Whichever server happens to be busiest starts refusing legitimate traffic while others sit idle with unused budget.

The divisor changes without warning. Autoscaling adds an instance and every limit is now wrong until something recomputes them. Deploys, restarts, and failed health checks all move the number.

It rounds badly. A limit of 10 across 8 servers is 1.25 each. Round down and the real limit is 8; round up and it's 16. Small limits — exactly the ones used for expensive operations like login or password reset — suffer most.

Fix 2: route each client to one server

If every request from a client always reaches the same instance, per-instance counting is per-client counting, and the arithmetic is correct again. Set the widget's routing to sticky by client — the total drops back to exactly 10.

This genuinely works and it is genuinely used. It costs you two things.

The limiter becomes coupled to your routing layer. Rate limiting now depends on consistent hashing by client id, so it can only be as correct as that routing is.

And rebalancing resets counters. Add or remove a server and some clients move to an instance that has never heard of them, arriving with a fresh budget. During a deploy — when your fleet is least able to absorb it — a portion of clients get their limits reset. That's tolerable for fairness limiting and unacceptable for abuse limiting, which is precisely when an attacker is watching for it.

Fix 3: one shared counter

Put the counter in Redis. Every instance increments the same key, so the limit is exactly right regardless of fleet size or routing.

count = INCR key
if count == 1: EXPIRE key window
if count > limit: refuse

Correct, simple, and it makes your rate limiter a distributed system with a hard dependency on the request path. Every request now costs a network round trip before you know whether to serve it. Under load that's the moment Redis becomes your bottleneck — and if it's unreachable you must choose, in advance, between failing open (no limiting during an incident, exactly when you need it) and failing closed (a Redis blip becomes a total outage).

That choice deserves a deliberate answer rather than a default. Most teams fail open for fairness limiting and closed for abuse limiting, which is a reasonable split, but only if someone decided it.

What production systems mostly do

Approximate, on purpose.

Each instance keeps a local counter and enforces immediately with no network call. Periodically — every second or so — instances share their counts through a shared store or gossip, and each adjusts its local budget based on what the fleet has spent. Between syncs the limit is slightly wrong; over any window that matters, it is close.

You trade exactness for the request path staying fast and staying up. Given that a limit of "100 per minute" was itself a rough guess, defending its last few units with a synchronous dependency on the hot path is usually the wrong trade.

The honest summary

There is no free exact distributed rate limiter. Every option trades exactness, latency, or a dependency — and the right answer depends on which of the four jobs from post 1 you're actually doing. A billing limiter should pay for a shared store. A capacity limiter should not.

The last post is about what to send when you do refuse. It turns out a bare 429 is close to useless, and the difference between a good refusal and a bad one decides whether clients back off or start hammering you harder.
