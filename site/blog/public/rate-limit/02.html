The boundary burst

Twice your limit, in two seconds, without breaking a single rule you wrote down.

Here is the attack, and it needs no tooling: a limit of 10 per minute, ten requests at 0:59, ten more at 1:01.

Both groups obey the policy. The first ten fall in the window ending at 1:00 and the counter allows them. The second ten fall in the next window, where the counter has just reset to zero, so it allows them too. The server, asked afterwards, will insist it never exceeded 10 per minute — and it will be telling the truth about its own counters.

These aren't estimates. They come from the simulator this page runs, which has a test asserting each number exactly — so if the arithmetic ever drifts, the test fails rather than this post quietly becoming wrong.

Sliding window log: exact, and expensive

Keep a timestamp for every request. On each new one, discard anything older than the window and count what's left.

log = log.filter(t => t > now - window)
if log.length < limit: log.push(now); allow
else: refuse

There is no boundary to exploit, because there is no boundary — the window is always the last 60 seconds measured from now. It is exactly correct by construction.

The cost is memory, and it scales with the wrong thing: one timestamp per request per client. A limit of 10,000 per minute means storing up to 10,000 timestamps for every client, and the clients generating the most load are the ones costing you the most memory. That's precisely backwards from what you want under attack.

Sliding window counter: two numbers, one assumption

Keep the count for the current window and the previous one. Weight the previous by how much of it still overlaps the trailing window:

elapsed = now - windowStart
overlap = (window - elapsed) / window
estimate = previousCount * overlap + currentCount
if estimate < limit: allow

Two integers per client, regardless of traffic. The boundary hole closes because the previous window's requests keep counting, fading out gradually instead of vanishing at a stroke.

Why it allows 11, not 10

The formula assumes the previous window's traffic was spread evenly. In this attack it wasn't — all ten arrived in the final second.

At 1:01 we're one second into the new window, so the previous one is weighted 59/60 = 0.983. The estimate reads 10 × 0.983 = 9.83, which is under 10, so one more request slips through before the count catches up.

That overshoot is the price of storing two integers instead of every timestamp. Worth knowing precisely: it's bounded and small, not a hole an attacker can widen.

The sliding counter is what most production systems use, and this table is why. It costs the same as the naive approach, removes the exploit, and its error is a fraction over the limit rather than a multiple of it. Cloudflare, and most API gateways, land here.

Reach for the log only when being exactly right matters more than memory — metering you bill customers for, say, where allowing an extra request is a rounding error you have to explain.

The general shape

Every algorithm here answers the same question with a different memory budget, and the differences only appear under adversarial traffic. Benchmarks against ordinary load would have shown all three as equivalent — which is exactly why the boundary burst is the pattern worth testing against.
