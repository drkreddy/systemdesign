Rate limiting · post 3 of 5

Token bucket: allowing bursts on purpose

The window algorithms all treat a burst as something to survive. Token buckets treat it as something to budget for — which is usually closer to what you actually want.

Real clients are bursty. A page loads and fires twelve requests at once. A mobile app comes back from the background and syncs. A cron job wakes at midnight with everything queued behind it. None of that is abuse, and a limiter that refuses it is refusing normal behaviour.

Window algorithms can't express this. They have one number, and it has to serve two purposes at once: how much sustained traffic do I permit, and how much can arrive at once. Set it low and you break legitimate bursts. Set it high and you permit sustained load you can't handle.

Two numbers instead of one

A token bucket separates them. Tokens drip in at a fixed rate; the bucket holds at most burst of them. Each request spends one, and a request with no token available is refused.

tokens = min(burst, tokens + elapsed * rate)
if tokens >= 1: tokens -= 1; allow
else: refuse

The consequences fall out of those two lines. Sustained throughput can never exceed the refill rate, because that's the only source of tokens. A client that has been quiet accumulates up to a full bucket, so it can burst that much instantly. And the bucket is a hard ceiling — idling for an hour doesn't earn an hour's worth of credit.

Drag the controls. The traffic is fixed: twenty requests at once, then steady arrivals afterwards.

allowed refused

Worth doing deliberately: set the bucket to 1 and you have a pure rate limiter with no burst tolerance at all — the opening twenty collapses to a single allowed request. Then raise the bucket while leaving the refill rate alone. The sustained portion behaves identically; only the opening burst changes. That separation is the whole feature.

rate
Sustained throughput. Over a long enough period, this is the only number that matters.
burst (bucket size)
How much a client that has been quiet may spend at once. Also the maximum credit that can ever accumulate.

Leaky bucket, and why it's the same picture upside down

You'll see leaky bucket named alongside token bucket as though they're alternatives. They're duals: a token bucket meters permission to enter, a leaky bucket meters departure, holding arrivals in a queue that drains at a fixed rate.

The practical difference isn't the algorithm, it's what happens to excess traffic. A token bucket refuses it — the client learns immediately and can retry. A leaky bucket queues it — the client waits, and under sustained overload that queue becomes latency nobody asked for, then a memory problem, then a queue full of requests whose callers gave up long ago.

For an HTTP API you almost always want to refuse. A fast 429 the client can act on beats a slow 200 nobody is waiting for any more. Queueing belongs where the work is genuinely asynchronous and the caller isn't blocked.

The question that picks the algorithm

Not "which is best" — it's "is a burst acceptable?" If yes, you need two numbers, and that means a token bucket. If no, one number is enough and a sliding counter is the cheapest way to enforce it honestly.

So far everything on this page has been a single limiter, holding its counters in one place. That assumption survives exactly as long as you run one server. Post 4 is about what happens to all of this when there are twenty of them, each counting on its own.
